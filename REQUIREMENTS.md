Ниже представлен подробный проект **Технических требований (Software Requirements Specification)** на разработку полнофункционального фреймворка для создания крупных и масштабируемых веб-приложений.

**Статус документа:** целевой SRS, а не гарантия реализованной функциональности или production readiness.
Текущая область поддержки и экспериментальные возможности определены в
[контракте поддержки](docs/guide/support.md), сверка требований с кодом и тестами —
в [реестре гарантий](docs/guide/guarantees.md). В частности, наличие Oracle/SQL Server dialect
не означает проверку на реальных СУБД; готовые Redis/RabbitMQ queue SDK adapters отсутствуют.

# Спецификация требований на разработку веб-фреймворка (кодовое имя: `Chitu Framework`)

## 1. Введение и общие положения
**Цель:** Разработка полнофункционального, высокопроизводительного и масштабируемого фреймворка на языке Golang для создания корпоративных веб-приложений, административных панелей, микросервисов и CLI-инструментов. 
Фреймворк должен концептуально наследовать архитектуру и удобство разработки (DX) фреймворка **Yii2**, но использовать современные асинхронные возможности Golang и современный фронтенд-стек (Vue 3 + AdminKit UI 3.5.0).

**Целевая аудитория фреймворка:** Крупные команды разработки, аутсорсинговые компании, корпоративный сектор.

---

## 2. Архитектура и базовые принципы (Ядро)
Фреймворк должен быть построен с учетом идиоматического стиля Go, избегая излишней магии (в отличие от PHP), но предоставляя привычные для Yii2 паттерны через интерфейсы и внедрение зависимостей.

### 2.1. Жизненный цикл приложения (Application Lifecycle)
*   **Точка входа:** Единый паттерн инициализации приложения (аналог `Yii::createObject` и `yii\web\Application`).
*   **Контейнер внедрения зависимостей (DI):** Встроенный или легко интегрируемый IoC-контейнер с поддержкой автоматического разрешения зависимостей (через рефлексию и интерфейсы) для контроллеров, моделей и экшенов.
*   **Событийная модель (Event Bus):** Поддержка подписки на события (аналог `Event` в Yii2) для разслабления связности компонентов (до/после запроса, сохранение модели, ошибки и т.д.).
*   **Поведение (Behaviors):** Механизм расширения функциональности структур без изменения их исходного кода (реализация через композицию интерфейсов или паттерн "Декоратор").
*   **Модульность (Modules):** Поддержка модульной архитектуры. Приложение должно состоять из модулей (аналог `yii\base\Module`), позволяя создавать изолированные домены (например, `admin`, `api`, `frontend`).

### 2.2. Компоненты приложения (Application Components)
Глобальный доступ к сервисам (аналог `Yii::$app`):
*   `db` (База данных)
*   `cache` (Кэширование)
*   `session` (Сессии)
*   `user` (Аутентификация)
*   `authManager` (RBAC)
*   `request` / `response`
*   `urlManager` (Роутинг)
*   `log` (Логирование)

## 3. Подсистема работы с базами данных (DB)
Критически важный компонент. Должен обеспечивать поддержку любых реляционных СУБД через абстракцию.

### 3.1. Универсальный интерфейс подключения (Connection)
Аналог `yii\db\Connection`.
*   **Интерфейс:** Должен предоставлять единый интерфейс для подключения к БД с использованием пула соединений стандартной библиотеки `database/sql`.
*   **Драйверы (из коробки):** Поддержка `PostgreSQL`, `MySQL/MariaDB`, `Oracle`, `Microsoft SQL Server`.
*   **Расширяемость:** Возможность добавления новых диалектов сторонними разработчиками без изменения ядра фреймворка (интерфейс `Driver` / `Dialect`).
*   **Конфигурация:** Поддержка настройки пула соединений (`MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime`), чтение конфигурации из переменных окружения (`.env`) и конфигурационных файлов.
*   **Транзакции:** Удобная обертка для работы с транзакциями (включая поддержку вложенных транзакций / savepoints).

### 3.2. Конструктор запросов (Query Builder)
Аналог `yii\db\Query`.
*   Флюент-интерфейс (Fluent Interface) для построения SQL-запросов (`Select`, `From`, `Where`, `Join`, `GroupBy`, `Having`, `OrderBy`, `Limit`).
*   Безопасная подстановка параметров (защита от SQL-инъекций).
*   Специфичная генерация SQL под диалект подключенной БД.

### 3.3. Active Record (ORM)
Аналог `yii\db\ActiveRecord`.
*   **Генерация кода (рекомендуется):** Так как в Go нет динамических свойств, модели должны генерироваться на основе схемы БД (аналог Gii) в виде структур со встроенными тегами.
*   **Методы:** `Find()`, `Save()`, `Insert()`, `Update()`, `Delete()`.
*   **Связи (Relations):** Поддержка `HasOne`, `HasMany` (через ленивую и жадную загрузку).
*   **Оптимистичная блокировка:** Поддержка версионирования записей при конкурентном доступе.
*   **Массовое присвоение (Mass Assignment):** Безопасное заполнение полей модели из форм/запросов с учетом сценариев валидации.

### 3.4. Миграции (Migrations)
*   CLI-инструмент для создания, применения и отката миграций (аналог `yii migrate`).
*   Поддержка транзакционных миграций.
*   Автоматическое определение примененных миграций (хранение в таблице БД).

## 4. Веб-слой и Маршрутизация (Web)
Фреймворк должен быть готов к созданию как классических многостраничных приложений (с рендерингом шаблонов на сервере), так и современных SPA/API-first решений.

### 4.1. Маршрутизация (URL Manager)
*   Поддержка строгих маршрутов и маршрутов с регулярными выражениями.
*   Именованные маршруты (генерация ссылок по имени).
*   Группировка маршрутов (с общими middleware, префиксами, доменами).
*   Поддержка маршрутизации модулей и контроллеров (паттерн `module/controller/action` или `controller/action`).

### 4.2. Контроллеры и Экшены
*   Базовый контроллер с методами `BeforeAction` и `AfterAction` (аналог `beforeAction`/`afterAction` в Yii2).
*   Поддержка аргументов в экшенах через DI (внедрение зависимостей в сигнатуру метода).
*   **Фильтры (Middleware):** Механизм пред- и пост-обработки запросов (аналог `yii\base\ActionFilter`): аутентификация, проверка прав, кэширование, ограничение частоты запросов (Rate Limiter).

### 4.3. Request и Response
*   Унифицированный объект контекста запроса.
*   Автоматическое парсинг входящих данных: `JSON`, `XML`, `Form-Data`, `Query Params`.
*   Гибкий Response: отдача `HTML`, `JSON`, `XML`, файлов, потоков (Stream), редиректов с нужными заголовками.

### 4.4. Шаблоны и Представления (Views)
*   Интеграция со стандартным `html/template` (или быстрым аналогом), но с механизмом **Наследования шаблонов (Layouts)**.
*   Поддержка Виджетов (аналог `yii\base\Widget`): переиспользуемые блоки кода (меню, пагинация, алерты).
*   **Интеграция с Vue 3:** Механизм передачи данных из Go в клиентские компоненты Vue (через теги `<script>` с сериализацией данных, аналог `@vite` и `Inertia.js`, либо классический API).

## 5. Frontend и UI (Vue 3 + AdminKit 3.5.0)
Фреймворк должен предоставлять готовую экосистему для быстрой разработки административных интерфейсов.

### 5.1. Интеграция Админ-шаблона
*   Из коробки фреймворк должен содержать настроенный базовый шаблон (каркас) на базе **AdminKit UI 3.5.0** (Bootstrap 5).
*   Реализованные страницы из коробки: Авторизация (Вход/Регистрация/Восстановление пароля), Панель управления (Дашборд), Страница профиля, Страница ошибки (404, 500).

### 5.2. Сборка фронтенда (Asset Management)
*   Встроенный инструмент или конфигурация для сборки фронтенда с помощью **Vite**.
*   Управление зависимостями: автоматическая сборка и минификация Vue-компонентов, CSS/SASS.
*   Механизм `AssetBundle` (аналог из Yii2): связь между серверными шаблонами Go и клиентскими скриптами/стилями. Поддержка хэширования версий файлов для кэширования.

### 5.3. Готовые UI Компоненты (Виджеты)
Серверные хелперы или Vue-компоненты для интеграции с AdminKit:
*   Таблицы данных (DataGrid) с серверной пагинацией, сортировкой и фильтрацией (связка Go QueryBuilder + Vue).
*   Формы (генерация форм из моделей валидации).
*   Компоненты алертов (Flash-сообщения).

## 6. Валидация данных и Модели
*   **Механизм правил (Rules):** Декларативное описание правил валидации в структурах (через теги или методы). Аналог `rules()` в Yii2.
*   **Валидаторы из коробки:** `required`, `string`, `integer`, `email`, `match` (regexp), `unique` (проверка в БД), `exist`, `compare`, `date`, `file`, `safe`.
*   Возможность создания кастомных валидаторов.
*   **Сценарии валидации:** Возможность валидировать одну модель по-разному для разных экшенов (например, `create` vs `update`).

## 7. Безопасность (Security)
Фреймворк должен соответствовать стандартам безопасности уровня Enterprise (защита от топ-10 угроз OWASP).

### 7.1. Аутентификация и Управление доступом
*   **Интерфейс `Identity`:** Аналог `yii\web\IdentityInterface`.
*   **Компонент User:** Управление сессией пользователя, функциями `login()`, `logout()`, `isGuest`, `getId()`.
*   **RBAC (Role-Based Access Control):** Полноценная система контроля доступа на основе ролей и разрешений (аналог `yii\rbac\DbManager`).
    *   Иерархия разрешений.
    *   Привязка ролей к пользователям.
    *   Проверка прав на уровне контроллеров и шаблонов.

### 7.2. Защита приложения
*   **Защита от CSRF:** Автоматическая генерация и проверка токенов для форм и AJAX-запросов от Vue.
*   **Защита от XSS:** Автоматическое экранирование вывода в шаблонах.
*   **Криптография:** Компонент для хеширования паролей (Bcrypt/Argon2), симметричное/асимметричное шифрование данных, генерация случайных ключей.
*   **Заголовки безопасности:** Настройка `Content-Security-Policy`, `X-Frame-Options`, `HSTS` из конфигурации.

## 8. Масштабируемость и Производительность

### 8.1. Кэширование
*   Единый интерфейс `Cache`.
*   Драйверы из коробки: `Memory` (in-process), `Redis`, `Memcached`, `Database`.
*   **Инвалидация кэша:** Механизм тегирования кэша и инвалидации по зависимостям (аналог `TagDependency`, `DbDependency` в Yii2).
*   Кэширование фрагментов страниц (на сервере) и кэширование результатов запросов.

### 8.2. Асинхронные задачи (Queues)
*   Встроенный компонент `Queue` для фоновых задач (аналог `yii2-queue`).
*   Отправка задач в очереди (отправка писем, генерация отчетов) и обработка их воркерами в отдельных горутинах или отдельных процессах.
*   Поддержка брокеров: Redis, RabbitMQ, БД.

### 8.3. Сессии
*   Хранение сессий в `Memory`, `Cookie`, `Database`, `Redis`.

## 9. CLI-инструменты и Генерация кода (Console & Gii)
Для обеспечения высокой скорости разработки фреймворк должен включать мощный консольный инструмент.

### 9.1. Консольное приложение
*   Возможность создания консольных команд (аналог `yii\console\Controller`).
*   Доступ к тем же компонентам приложения (БД, кэш, модели), что и в вебе.

### 9.2. Генератор кода (Аналог Gii)
Web-интерфейс или CLI-инструмент для автоматической генерации:
*   **Миграций:** На основе структуры БД.
*   **Моделей (ActiveRecord):** Генерация Go-структур и методов связей из таблиц БД.
*   **CRUD:** Генерация контроллера, моделей поиска, экшенов и клиентских компонентов **Vue 3 / AdminKit** для создания, чтения, обновления и удаления сущностей.

## 10. Логирование, Отладка и Мониторинг

### 10.1. Логирование
*   Интеграция со стандартным `log/slog` (структурированное логирование).
*   Уровни: `Debug`, `Info`, `Warning`, `Error`, `Fatal`.
*   Цели (Таргеты): Запись в файлы, консоль, БД, отправка по сети (Syslog, Elasticsearch, Telegram и т.д.).

### 10.2. Панель отладки (Debug Toolbar)
*   Визуальная панель для разработки (внизу экрана).
*   Показывает: время выполнения запроса, потребление памяти, список выполненных SQL-запросов (с планами выполнения), роутинг, сессию, переменные окружения.

### 10.3. Метрики
*   Экспорт метрик приложения в формате `Prometheus` (количество запросов, время ответа, ошибки).
*   Поддержка трассировки запросов (например, через интеграцию с `OpenTelemetry` или `pprof`).

## 11. Требования к процессу разработки и поставке

### 11.1. Требования к коду
*   Код должен соответствовать стандартному стилю форматирования `gofmt` / `goimports`.
*   Использование линтеров (`golangci-lint`).
*   Покрытие тестами ядра фреймворка не менее **80%**.
*   Поддержка модульности (использование `go.mod`).

### 11.2. Документация
*   Наличие исчерпывающей документации (The Definitive Guide), аналогичной структуре документации Yii2:
    *   Введение и Установка.
    *   Структура приложения.
    *   Работа с БД и Миграции.
    *   Интеграция с Vue 3 и AdminKit.
    *   Описание всех компонентов ядра и API.
*   Сгенерированная документация по коду (через `godoc` / `pkg.go.dev`).

### 11.3. Демонстрационные приложения (Семплы)
Вместе с фреймворком должны поставляться 3 демонстрационных приложения:
1.  **Базовый каркас (Basic Project):** Минимальный сайт с авторизацией и дашбордом AdminKit.
2.  **Корпоративная админка (Advanced Admin):** Пример реализации RBAC, CRUD, справочников, ролей и разрешений.
3.  **API Сервис (REST API):** Пример создания микросервиса на базе фреймворка (только отдача JSON, авторизация по JWT).


### 12 Мультиязычность
Фреймворк должен поддерживать мультиязычность, должна быть возможность переключать язык и задавать сообщения на выбранном языке.


### Дополнения
Комментарии к коду оставляй на русском языке, код пиши и читай в кодировке UTF-8; используй Docker для разворачивания и проверки т.к. на локальной машине не установлен Golang; 
не используй внешние зависимости, если в этом нет необходимости; На каждый функциональный блок обязательно должены быть написаны тесты; 
план разработки проекта веди в файле PLAN.md; архитектурные решения и компоненты ситемы и их взаимодействие записывай в файле ARCHITECTURE.md; 
в файле README.md веди документацию по разворачиванию фреймворка и его использованию;

### Стек технологий
Golang 1.26; VueJS 3; AdminKit UI 3.5;

### Принципы реализации и имя модуля
* Разработку вести в идиоматическом стиле Go: использовать явные зависимости и обработку ошибок, композицию вместо наследования, небольшие интерфейсы и минимально необходимую рефлексию.
* Архитектуру фреймворка и Developer Experience проектировать на основе Yii2, адаптируя его компоненты и паттерны к модели языка Go без буквального переноса PHP-идиом и динамической магии.
* Каноническое имя Go-модуля и базовый путь импортов: `github.com/chitushka/framework`.

### Фиксация результатов разработки
* После реализации очередного шага из `PLAN.md`, успешного выполнения предусмотренных тестов и обновления документации изменения необходимо зафиксировать отдельным git-коммитом.
* Заголовок или описание коммита должно содержать краткое и конкретное описание реализованной функциональности.
* Один коммит должен соответствовать одному логически завершённому шагу плана; незавершённые или не прошедшие проверки изменения не должны отмечаться в `PLAN.md` как выполненные.
* Запрещено отправлять изменения в удалённый репозиторий (`git push`) или иным способом автоматически публиковать локальные коммиты. Публикацию изменений выполняет только владелец проекта вручную.
