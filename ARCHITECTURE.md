# Архитектура Chitu Framework

## Принципы

- Реализация следует идиоматическому Go: явные зависимости и ошибки, небольшие интерфейсы на стороне потребителя, композиция вместо наследования и минимально необходимая рефлексия.
- Yii2 служит архитектурной и DX-основой: из него заимствуются проверенные границы компонентов, жизненный цикл, модули, события, behaviors, Active Record, URL Manager и подходы Console/Gii. PHP-идиомы и динамическая магия Yii2 не переносятся буквально, если они противоречат модели Go.
- Ядро использует только стандартную библиотеку Go.
- Компоненты зависят от малых интерфейсов; конкретные реализации связываются в точке сборки.
- Неявная магия ограничена проверяемой рефлексией DI-контейнера.
- Запуск и остановка имеют явный порядок, принимают `context.Context` и возвращают ошибки.
- Пакеты верхнего уровня не импортируются ядром, поэтому web, db, cache и прочие подсистемы можно использовать независимо.

## Имена пакетов

Имена `app`, `di`, `event` и `web` оставлены намеренно: они короткие, строчные, однословные и не повторяют module path. `di` является устоявшимся техническим сокращением. Пакеты именуются по предоставляемой области ответственности, а не по отдельному типу или слою Yii2.

## Текущие компоненты

```text
Application
  ├── DI Container
  ├── Event Bus
  ├── Config Loader
  ├── Component Registry
  ├── Behavior Decorators
  └── Modules (register → boot → shutdown)
```

### `di`

Контейнер хранит определения по `reflect.Type`. Зависимости создаются конструкторами либо автоматической сборкой указателей на структуры. Поля для автоматического внедрения помечаются `di:"inject"`. Интерфейс связывается с реализацией явно. Singleton создаётся через `sync.Once`; циклы зависимостей обнаруживаются до вызова конструктора.

### `event`

Локальная типизированная по имени шина событий. Обработчики имеют приоритет и стабильный порядок регистрации. Последовательная публикация подходит для lifecycle hooks, конкурентная — для независимых обработчиков. Ошибки объединяются через `errors.Join`.

### `app`

`Application` владеет контейнером, шиной, реестром компонентов и модулями. Регистрация всех модулей выполняется до их запуска. При ошибке `Boot` уже запущенные модули останавливаются в обратном порядке. Обычная остановка также идёт в обратном порядке. Модули могут реализовать `ErrorSource`: тогда `Application.Run` отслеживает runtime-ошибку, останавливает приложение и возвращает её вызывающему коду.

### `web`

HTTP-слой построен поверх `net/http`: `Router` реализует `http.Handler`, а framework handler возвращает ошибку вместо самостоятельной отправки аварийного ответа. `Context` хранит request/response и параметры маршрута. Middleware являются обычными функциями-декораторами. Маршруты регистрируются до начала обслуживания запросов, после чего чтение таблицы маршрутов безопасно конкурентно. URL Manager поддерживает вложенные группы, route/group middleware, host-шаблоны и ограничения параметров регулярными выражениями RE2. Именованный host-маршрут генерирует protocol-relative URL, не навязывая приложению HTTP или HTTPS. Controller action задаётся method expression вида `(*UserController).Show`: первый аргумент разрешается как контроллер, `*web.Context` берётся из текущего запроса, остальные аргументы разрешаются через DI. Контроллер реализует lifecycle `BeforeAction`/`AfterAction`, обычно встраивая no-op `BaseController`; ошибка before-hook останавливает action, а ошибки action и after-hook сохраняются совместно. Такой контракт оставляет сигнатуры проверяемыми компилятором и не вводит строковый поиск методов. Response API контекста поддерживает HTML, JSON, XML, streams, inline files и downloads. Структурированные ответы сериализуются до отправки заголовков, file response определяет тип содержимого и выставляет длину и время изменения, а ошибки чтения и записи сохраняют исходную причину через `%w`. После начала ответа централизованный error handler не пытается записать второе тело. `Renderer` загружает независимые `html/template` из любого `fs.FS` и безопасен для конкурентного выполнения после создания. View сначала полностью рендерится с автоматическим экранированием, затем передаётся layout как доверенный результат шаблонизатора; исходные данные доступны layout отдельно. Widgets используют тот же механизм и встраиваются функцией `widget`. `VueState` помещает JSON в `application/json` script, полагаясь на обязательное escaping символов `<`, `>` и `&` в `encoding/json`, поэтому пользовательские данные не могут закрыть script-тег. Ошибка view или layout возникает до начала HTTP-ответа. `web.Server` является модулем приложения: listener открывается синхронно в `Boot`, запросы обслуживаются асинхронно, а `Shutdown` прекращает приём соединений и ожидает активные запросы в пределах настроенного таймаута.

### `db`

`Connection` владеет настроенным пулом `database/sql` и выбранным SQL-диалектом. `Open` валидирует конфигурацию, применяет лимиты и времена жизни соединений, затем синхронно выполняет `PingContext`; при ошибке созданный пул закрывается. Конкретный `database/sql/driver` регистрируется отдельным модулем и не импортируется ядром. `DialectRegistry` потокобезопасен и отделяет имя драйвера от правил SQL-синтаксиса. Встроенные диалекты PostgreSQL, MySQL/MariaDB, Oracle и SQL Server определяют quoting идентификаторов и placeholders; сторонний диалект реализует малый интерфейс `Dialect` и регистрируется явно. `Connection` предоставляет стандартные `ExecContext`, `QueryContext`, `QueryRowContext`, `PrepareContext`, статистику пула и доступ к нижележащему `*sql.DB` для сценариев, не покрытых фреймворком. `Transaction` оборачивает корневой `sql.Tx`; вложенные транзакции работают на том же соединении через optional-интерфейс `SavepointDialect`. Имена savepoints генерируются внутри фреймворка и не содержат пользовательский ввод. Активная дочерняя транзакция временно блокирует операции и завершение родителя, предотвращая перепутанный lifecycle. PostgreSQL/MySQL освобождают savepoint явно, Oracle и SQL Server оставляют его до завершения внешней транзакции согласно возможностям СУБД. Callback API выполняет commit только после успеха, откатывает всю незавершённую вложенную цепочку при ошибке или panic и объединяет callback/rollback-ошибки через `errors.Join`. Active Record расположен в отдельном пакете `db/ar`: `Repository[T]` явно связывает структуру и таблицу, optimistic locking является частью SQL-условия обновления, eager relations выполняются пакетно, а генерация моделей опирается на стандартные метаданные `database/sql` и явные непереносимые настройки ключей.

SQL-вызовы `Connection` и `Transaction` уведомляют необязательный `QueryObserver`, установленный в `context.Context`. Без observer путь остаётся allocation-free относительно диагностических событий; debug toolbar использует этот контракт, не создавая обратной зависимости `db` от web/debug.

### `validation`

Правила валидации являются обычными значениями и выполняются через малый интерфейс `Validator`; ожидаемые нарушения данных представлены отдельно от операционных ошибок. Сценарий содержит явный allowlist внешних имён полей и одновременно ограничивает активные правила. Массовое присваивание сначала конвертирует все допустимые значения во временное представление и только после полного успеха изменяет модель, поэтому не оставляет частичного состояния. Неизвестные и неразрешённые поля игнорируются с явным отчётом. Проверки `Unique` и `Exist` используют Query Builder и не интерполируют значения в SQL.

### `cache`

`Cache` отделён от минимального байтового `Backend`: общий `Store` отвечает за TTL-метаданные, копирование значений, теги, произвольные `Dependency` и безопасную обработку повреждённых записей, а backend — только за `Get`/`Set`/`Delete`. Физические ключи имеют фиксированную длину и строятся через SHA-256 из префикса, поколения пространства и пользовательского ключа, что одновременно выполняет ограничения Memcached и не раскрывает исходные ключи. `Clear` и теговая инвалидация меняют случайные поколения, поэтому не требуют небезопасного `FLUSHDB`, `flush_all` или распределённого перебора ключей.

Memory backend синхронизирован `RWMutex` и копирует срезы на границах. Redis и Memcached реализуют ограниченные необходимые подмножества RESP2 и текстового протокола стандартной библиотекой, открывают соединение с context-aware dial и ограничивают каждую операцию deadline. Database backend зависит от `database/sql`-совместимого интерфейса и `db.Dialect`, валидирует имя таблицы, использует placeholders и разрешает конкурентную пару update/insert повторным update. `DBDependency` хэширует типизированное представление всех строк запроса; callback-вычислители принадлежат экземпляру `Store`, поэтому запись из другого процесса без локального вычислителя считается промахом, а не возвращается потенциально устаревшей.

### `session`, `auth`, `security`

`session.Manager` хранит на клиенте только криптографически случайный идентификатор, а JSON-состояние передаёт заменяемому `Backend`. `MemoryBackend` предназначен для одного процесса; `NewBackend` адаптирует минимальный key-value контракт, который уже реализуют Redis и Database backends пакета `cache`, не связывая пакеты конкретными типами. Для небольшого stateless-состояния `CookieStore` шифрует и аутентифицирует всё содержимое через AES-GCM, ограничивает размер и считает повреждённый cookie новой сессией. Запись выполняется до HTTP-заголовков. Cookie всегда имеет `HttpOnly` и `SameSite=Lax` по умолчанию, а `Secure`, domain, path и TTL задаются конфигурацией. Смена идентификатора при login/logout защищает от session fixation.

`auth.Identity` содержит только стабильный строковый ID, а приложение восстанавливает доменный объект через `IdentityLoader`. Middleware создаёт отдельный `auth.User` для запроса; `Login`, `Logout`, `IsGuest`, `ID` и `Identity` не используют глобальное состояние. Отсутствующая после загрузки identity превращает сессию в гостевую. `RequireAuthenticated` и `RequireGuest` являются обычными middleware.

CSRF middleware создаёт независимый session-bound токен, принимает его из `X-CSRF-Token` для Vue/fetch или `_csrf` для HTML-форм и сравнивает в constant time. Безопасные HTTP-методы пропускаются, остальные получают `403` при отсутствии или несовпадении токена. Middleware заголовков выставляет настраиваемые CSP, HSTS и Referrer-Policy, а также безопасные значения `X-Frame-Options` и `X-Content-Type-Options` по умолчанию. Пакеты `session`, `auth` и `security` содержат HTTP-адаптеры поверх малого публичного контракта `web.Handler`; зависимость направлена только к HTTP-слою, а `web` не знает о прикладных подсистемах.

### `rbac`

`rbac.Manager` отделяет политику от хранения через интерфейс `Store`. Роль может наследовать роли и разрешения, разрешение — только другие разрешения; добавление ребра предварительно проверяет достижимость и отклоняет циклы. Пользователю назначаются только роли. Проверка доступа обходит все назначенные роли до целевого разрешения и выполняет именованные runtime-правила на каждом выбранном пути; отказ правила отсекает его поддерево, а ошибка передаётся вызывающему коду. Правила получают user ID и типизированные параметры запроса, поэтому object-level policy не встраивается в HTTP-слой.

`MemoryStore` синхронизирован и предназначен для тестов или одного процесса. `DatabaseStore` хранит элементы, рёбра и назначения в трёх нормализованных таблицах с составными первичными ключами и каскадными внешними ключами; DDL формируется для зарегистрированного SQL-диалекта и применяется обычной миграцией приложения. `Require` связывает проверку с текущим `auth.User` и возвращает `401` гостю либо `403` пользователю без разрешения. `TemplateFunc` предоставляет fail-closed helper для `html/template`, не раскрывая инфраструктурные ошибки в представлении.

### `queue`

Очередь разделена на сериализующий `Queue`, подтверждаемую доставку `Broker` и исполняющий `Worker`. Сообщение содержит случайный ID, имя обработчика, JSON payload, номер попытки и предел повторов. Успешная задача подтверждается через `Ack`; ошибка до предела попыток возвращает её через `Nack` с настраиваемой задержкой, а окончательная ошибка подтверждает и удаляет сообщение после вызова `OnFailure`. Такая модель сохраняет at-least-once delivery: обработчики должны быть идемпотентными. `JSONHandler[T]` декодирует payload в тип приложения без reflection-реестра типов.

`MemoryBroker` использует синхронизированную приоритетную очередь и поддерживает отложенную доставку в одном процессе. `DatabaseBroker` резервирует строку условным update с уникальным receipt; истёкшая lease позволяет другому процессу восстановить задачу после падения worker. DDL учитывает четыре встроенных SQL-диалекта. `RedisBroker` зависит от малого `RedisStore`, который атомарно переносит due-message в leased-состояние; `RabbitMQBroker` адаптирует publish/consume/ack AMQP-клиента и при retry сначала публикует новую попытку, затем подтверждает исходную доставку. Сетевые интеграции вынесены в интерфейсы, поэтому framework не закрепляет версию стороннего Redis/AMQP SDK.

`Worker` запускает заданное число goroutine, не принимает изменение реестра после запуска и завершает активный цикл через `Shutdown`. Он реализует `app.Module` и `app.ErrorSource`: критическая ошибка broker/ack останавливает соответствующего consumer и передаётся lifecycle приложения, а обычная ошибка job остаётся частью retry-policy. Тот же worker запускается в отдельном процессе или как модуль общего приложения.

### `i18n`

Интернационализация отделяет выбор locale, хранение сообщений и форматирование. `Locale` канонизирует BCP 47-подобные теги (`ru_RU` → `ru-RU`), `Matcher` выбирает только явно поддерживаемый язык с переходом к родительскому тегу, а parser `Accept-Language` учитывает quality. Locale хранится в request context, поэтому переключение языка не использует глобальное изменяемое состояние и безопасно при конкурентных запросах.

Каталог загружается из `fs.FS` по соглашению `<locale>/<category>.json`; значение является строкой либо объектом CLDR plural forms. `Translator` ищет сообщение по цепочке requested → parents → configured fallbacks → default, параметризует его через `text/template` с обязательными ключами и по умолчанию возвращает message key при отсутствии перевода. Plural rules встроены для английского/романского, славянского и арабского семейств. Результат остаётся обычной недоверенной строкой, поэтому `html/template` продолжает автоматически экранировать пользовательские параметры и сам перевод.

HTTP middleware выбирает язык в порядке query parameter, cookie, `Accept-Language`, default; записывает `Content-Language`, корректно дополняет `Vary` и сохраняет явный выбор в `SameSite=Lax` cookie. Template helpers `t`/`tn` требуют явный locale, что не связывает неизменяемый глобальный `Renderer` с конкретным запросом.

### `console`, `gii`

`console.Application` является однократным диспетчером команд поверх обычного `app.Application`: перед выполнением команды он запускает lifecycle модулей, передаёт команде тот же component registry и всегда вызывает shutdown. Команды реализуют малый интерфейс либо задаются `CommandFunc`, регистрируются до запуска и получают context/stdout/stderr без прямого завершения процесса. `help` сортирует команды детерминированно. Стандартный toolset адаптирует существующий migration CLI и добавляет `generate:migration`, `generate:model`, `generate:crud`; SQL-драйвер остаётся выбором приложения через blank import.

Генераторы читают схему через `ar.DatabaseInspector`. Migration generator строит обратимую пару `CREATE/DROP TABLE`, экранирует идентификаторы выбранным диалектом, переносит primary key, nullable и auto-increment и отклоняет небезопасный SQL type. Model generator переиспользует существующий gofmt-форматированный Active Record generator. CRUD generator создаёт JSON controller с пятью actions и регистрацией маршрутов, отдельную allowlist search model и Vue 3/AdminKit-compatible таблицу/форму. Input DTO исключает primary/auto/version поля и присваивает только явно переданные значения. Все файлы создаются эксклюзивно; предварительная проверка и rollback не оставляют частичный scaffold и не перезаписывают пользовательский код.

### `asset`, Vue и Vite

`asset.Registry` хранит именованные AssetBundle, разрешает их зависимости топологически, устраняет повторяющиеся ресурсы и отклоняет отсутствующие или циклические зависимости. Stylesheets и `modulepreload` выводятся в `<head>`, scripts — в конце `<body>`; URL и значения атрибутов проходят контекстное escaping `html/template`. Registry копирует входные структуры при регистрации и создаёт snapshot перед разрешением, поэтому после публикации безопасен для конкурентных рендеров. `TemplateFuncs` связывает заранее выбранные bundles с `assetHead`/`assetBody`, не принимая имена из шаблона.

Production-интеграция читает `.vite/manifest.json`, рекурсивно собирает imports и CSS и сохраняет хэшированные имена Vite для cache busting. Development bundle подключает `@vite/client` и исходный entry с явно заданного HTTP(S) dev server. Готовый `frontend` использует Vue 3, Vite и зафиксированный `@adminkit/core` 3.5.0; production-файлы собираются в `public`, а manifest является контрактом между Node-сборкой и Go-приложением.

### `logging`, `observability`, `debug`

`logging` остаётся совместимым со стандартным `log/slog`: writer handlers покрывают console/file/network, `MultiHandler` выполняет fan-out в произвольные targets (включая прикладные DB/Elasticsearch/Telegram handlers), а wrapper `Logger` добавляет уровень Fatal с заменяемой функцией завершения процесса. Уровни и фильтрация делегированы `slog.Handler`, поэтому targets могут иметь разные thresholds и formats.

`observability.HTTP` оборачивает весь `http.Handler` и в одном lifecycle записывает структурированный request log, ограниченные по cardinality Prometheus-метрики и trace span. Метрики не используют raw URL как label и поэтому не создают неограниченные series. Tracer принимает/выдаёт W3C `traceparent`, хранит active span в request context и передаёт immutable snapshot заменяемым exporters; OpenTelemetry подключается адаптером без обязательной зависимости ядра от SDK. Стандартный pprof публикуется отдельным handler и требует явной авторизации/изоляции со стороны приложения.

`debug.Toolbar` является отключённым по умолчанию web middleware. Он буферизует только ответ текущего route, добавляет экранированную панель в успешный несжатый HTML и сохраняет исходное поведение JSON, streams и ошибок. Панель показывает duration/memory, route и params, trace ID, SQL events и переданные EXPLAIN plans. Session snapshot задаётся приложением, а environment имеет обязательный allowlist; SQL arguments скрыты по умолчанию. Эти ограничения не позволяют случайно превратить production toolbar в канал утечки секретов.

### `config`

Загрузчик заполняет пользовательские Go-структуры и не вводит глобальное хранилище. JSON-файлы накладываются в порядке объявления, затем применяются `.env`-файлы и окружение процесса. Поля связываются явно тегами `env`, `envDefault`, `envRequired`; поддерживаются скалярные типы, duration, slices, pointers и `encoding.TextUnmarshaler`. Такой API сохраняет типобезопасность и позволяет зарегистрировать готовую конфигурацию в DI как обычный singleton.

### `component`

`Application.Components` заменяет глобальный `Yii::$app` явной зависимостью. Реестр предоставляет именованные ленивые singleton-компоненты и transient-фабрики. Фабрика получает ограниченный `Resolver`, поэтому зависимости компонентов видимы в коде; циклы обнаруживаются по пути разрешения. Ошибка создания singleton не кэшируется и допускает повторную попытку. Встроенные имена приложения: `app`, `components`, `container`, `events`.

### `behavior`

Динамическое добавление методов из Yii2 заменено типобезопасными декораторами интерфейсов. `behavior.Apply` последовательно строит цепочку обёрток того же Go-интерфейса и останавливается с ошибкой при невозможности применить поведение. Декорированный объект можно зарегистрировать обычной фабрикой в `component.Registry` или DI.

## Правила дальнейшего развития

1. При конфликте между буквальным повторением API Yii2 и идиоматическим Go выбирается идиоматический Go с сохранением назначения и удобства исходного механизма.
2. `web`, `db`, `cache`, `queue`, `session`, `auth` могут зависеть от `di` и `event`, но не друг от друга без интерфейса.
3. Интеграции с Redis, RabbitMQ и конкретными SQL-драйверами размещаются в отдельных пакетах/модулях.
4. Публичные API получают unit-тесты одновременно с реализацией.
5. Обратная совместимость публичного API сохраняется после первого стабильного релиза.
